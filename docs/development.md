# Development

[Back to README](../README.md#documentation)

Common development commands:

```sh
make setup
make dev
make check
make security
make modernize-check
```

`make dev` runs Air with `ENV=dev` and
`LOG_LEVEL=debug`, builds a `dev`-versioned `./tmp/detent` with the current
commit SHA and build date, rotates
`tmp/air-combined.log`, and streams combined build and application output to
`tmp/air-combined.log`.

`make check` is an optional diagnostic suite: build, `golangci-lint`, `go vet`,
NilAway, race tests, and a coverage profile kept as evidence without a floor. Run `make generate`
after changing Templ templates or sqlc queries; stage their generated Go output.
Tailwind and documentation output are ignored and generated by their consumers.
`make security` runs the pinned `govulncheck` and standalone `gosec` scans used
by CI. The gosec baseline skips generated files and documents each legacy rule
excluded in the Makefile; new findings must be fixed or narrowly annotated.
`make modernize-check` runs the Go modernizer diff check with the repo's
selected safe analyzer set.

Follow the repository's [validation policy](../AGENTS.md#validation) and
[failure reporting policy](../AGENTS.md#deployment-and-release-failure-reporting).
Run `make check-land` before reporting source work complete, fix failures in the
same run, and report its printed wall time. It uses the scheduled lint version
and configuration, vet and baseline-aware NilAway, `go build ./...`,
`go test -short ./...`, invariants, migration and generated-source checks.
Conversation typecheck, vitest and build run when `web/conversation` differs
from the merge base with `origin/develop`, including staged, unstaged and
untracked changes. Set `CHECK_LAND_BASE` to the actual landing base when it
differs. A missing base ref fails the target. A fresh worktree builds missing
embedded conversation assets with Node 24; ignored bundles are never staged.
The target generates docs and checks SQL output once, then overlaps lint, vet,
build and short tests within `TEST_PROCS`. It prints its exit code and elapsed
seconds. Lint and vet
use the scheduled tools. If a
complete run exceeds ten minutes, report stage timings before moving expensive
integration or race diagnostics to the scheduled suite.

Workers run `make check-land` under this repository's validation instructions.
The Cloud project uses `gate.run: make check-landing` and
`gate.landing_mode: per_landing`; changes require operator re-approval in the Hub.
The GitHub landing path validates the combined tree with a build, short Go tests
for touched packages and their dependents, and lint of changed Go files. Module
changes widen the selection. The native landing path retains its existing
receipt and rebase validation. A command failure returns the item to Rework with
its output. Full browser, race, repository-wide NilAway and integration checks
stay in the scheduled suite and never hold landing. The host also uses the
approved short command during source finalization, so its durable receipt proves
that command. The full source gate remains the worker's completion requirement.
Browser journeys run in the scheduled full suite. For an explicit focused
diagnostic, run `bash scripts/check-browser.sh "$TEST_PROCS" false tests/visual/<journey>.spec.js`;
use `true` when the current conversation assets
are already prepared.
Focused diagnostics and full scheduled
suites do not publish a required local commit status. The
scheduled suite validates pinned develop commits and release branch heads;
only green release branch heads receive stable tags. See the
[release branch policy](branching.md#release-branches). Separately,
every failing Detent scheduled job enters native Todo at least High under the
human-approved reporting policy, including infrastructure and unclassified
failures. Reused job issues preserve Urgent, human questions and operator holds;
matching Backlog intake moves to Todo through the native workflow owner, while
active and review lanes remain intact. Other unknown instance diagnostics remain
in nondispatchable Backlog. A red suite receives no release tag.

Several worktrees usually run gates on the same host at once. `TEST_PROCS`
(default 4) supplies each invocation's process budget. `make check-landing`
runs its stages sequentially. Go builds and tests use at most `TEST_PROCS`
concurrent package processes with `GOMAXPROCS=1` in each, so their package and
scheduler budgets multiply to at most `TEST_PROCS`. Lint uses one runtime with
`GOMAXPROCS=TEST_PROCS` and at most `TEST_PROCS` workers. Asset and documentation
preparation inherit `GOMAXPROCS=1` and run through `make -j1`.
The landing short-test deadline is three minutes for each whole package,
including all its tests and fixtures; it is not a per-test allowance. Assertion
failures still fail the gate, and a hung package still hits the deadline.
This package allowance provides margin for legitimate aggregate suite costs
under shared-host contention and remains below the source gate's ten-minute
short-package allowance. It applies to every selected package without exceptions.
Standalone diagnostic targets set package, scheduler, lint and vitest worker
limits from `TEST_PROCS`; these separate limits do not by themselves bound their
product. Raise the budget per invocation when appropriate.
`make check-land` generates docs and checks SQL output once before overlapping
lint, vet, build and short tests. It divides `TEST_PROCS` among these stages,
running them in batches when the budget is below four. Unchanged conversation
sources need no frontend build or ignored bundle. Source completion retains repository
source/workflow invariant tests and migration checks; the full behavioral
invariant manifest and repository-wide NilAway audit run in the full suite.
Plain `go test ./...` outside `make` has no cap.

Ordinary `make test`, `make test-fast`, and `make check-land` reuse Go's native
test-result cache for unchanged packages and tracked inputs. Filesystem
diagnostics in tests use temporary directories or explicit fixtures rather than
walking host toolchain caches. Scheduled race and coverage targets use
`-count=1`, preserving fresh scheduled evidence.
Build and module caches retain their native locations.

Scheduled Windows portability runs the Hub suite through
`make test-hub-portability`, reusing the same three exhaustive, disjoint
partitions as the race targets with four parallel tests and a ten-minute budget
per partition. The remaining package selection excludes Hubserver and workspace,
which have already run separately. Evidence for each Hub partition is included
in the existing Windows test artifact. Test selection and individual deadlines
remain unchanged.

Portability Stress is a manually dispatched macOS/Windows diagnostic workflow.
Its suites run on separate hosted runners through
`bash scripts/portability-stress.sh <suite>`, with `GOMAXPROCS=4`, bounded test
parallelism, and evidence under the supplied `TMPDIR`, `TMP`, or `TEMP`.
The CLI, runner, and checklock suites retain ten race repetitions; the other
suites retain the complete race package selection, including one more run of
those three packages. Windows also retains twenty SQLite lifecycle repetitions.
Hubserver uses the same three disjoint test partitions as the Makefile, with
two parallel tests per partition. Orchestrator and workspace run separately;
the remaining packages run one at a time through the existing evidence tool.

The Windows diagnostic job in run `36678733180` took 4933.681 seconds for ten
CLI repetitions and 1205.368 seconds for checklock. Their package budgets are
120 and 45 minutes, with job budgets of 150 and 60 minutes respectively.
Runner has a 45-minute package budget. Hubserver partitions have 45-minute
budgets after the unpartitioned suite exceeded 30 minutes on both platforms;
orchestrator and remaining packages have 30-minute budgets, and workspace
retains its existing 15-minute budget. Job budgets leave time for setup and
evidence upload. These bound cumulative suite work; individual production
deadlines and test workloads remain unchanged. Hosted resource contention is
still a hypothesis. Uploaded JSON events include run/pause/cont timestamps for
diagnosing queue time separately from execution time.

Packages that own transport, hub, watcher, orchestrator, and runner goroutines
also run `go.uber.org/goleak` from package-level tests, so `go test ./...`,
race tests, and `make check` fail on unexpected goroutines. Add goleak ignores
only in the package that needs them, and only after identifying the dependency
or intentionally shared test goroutine.

Nil safety is enforced by `make check` and can also be run directly while
iterating:

```sh
make nilaway-audit
```

The scheduled audit uses `make nilaway-changed`. Despite its historical name,
it analyzes all Go packages so changes to a provider's inferred nilability also
check unchanged importers. It accepts only reviewed legacy diagnostics whose
location and source-line hash match `scripts/nilaway-baseline.json`.

The pinned analyzer runs through `go vet -vettool` with one package process at
a time, retaining dependency facts without loading the entire module's syntax
and type information into one process. Its default Go soft memory limit is
1 GiB; an explicit `GOMEMLIMIT` is preserved. This is a garbage-collection
target, not a hard RSS cap. The temporary binary uses the supplied `TMPDIR`,
`TMP`, or `TEMP`. Tool installation, package loading, and analyzer failures
remain failures even when another package emits reviewed baseline diagnostics.

The project uses the pinned NilAway command instead of golangci-lint
integration because the linter integration requires a custom module-plugin
binary. Go 1.26's experimental `runtime/pprof` `goroutineleak` profile remains a
runtime audit aid behind `GOEXPERIMENT=goroutineleakprofile`; the stable CI
coverage for now is the goleak-backed test gate.

## Concurrent migrations and generated files

New Goose SQL migrations in `internal/store/migrations` and
`internal/hubserver/migrations` use UTC timestamp versions:
`YYYYMMDDHHMMSS_name.sql`. Use a descriptive name and Goose's default timestamp
mode, never `-s` (sequential mode):

```sh
make db-create NAME=add_feature
make db-create NAME=add_feature MIGRATIONS_DIR=internal/hubserver/migrations
```

The target runs `TZ=UTC goose -dir "$MIGRATIONS_DIR" create "$NAME" sql`.
The equivalent direct command is
`TZ=UTC goose -dir internal/store/migrations create add_feature sql`.
Existing numbered files remain unchanged: store through 68 and Hub through 71.
The older descriptive-name boundaries (store 68, Hub 70, registry 5, auth 4)
remain fixed in the checker; registry and auth retain their sequential convention.
`make check-migrations` diagnoses duplicate versions and invalid timestamp names
in the existing scheduled suite or during optional focused diagnostics.

Adding a SQL migration changes only its new file. The embedded directory supplies
the migration set and supported Hub version; the historical Go data conversions
remain registered at their original versions. Timestamp versions sort after
every historical sequential version. Fresh databases apply them in version
order. Existing databases apply pending files through Goose, including older
timestamps that land after a newer timestamp, without renumbering at landing.
Hub foreign-key verification stays in the last pending migration's transaction,
including when that migration has an older timestamp than the database maximum.

Independent migrations with distinct timestamps merge in either order. Timestamps
have one-second precision, so simultaneous creation can still produce a duplicate
version; the checker reports it even when descriptive filenames differ. Choose a
distinct UTC timestamp before publishing an unapplied migration. Never rename or
renumber a migration that may already have been applied; use a forward repair for
deployed collisions. Migrations that depend on another branch's schema still
require their source dependency to land first and an appropriate version order.

sqlc reads `internal/store/migrations` through `sqlc/sqlc.yaml`, including timestamp
files. Run `make sqlc` after schema or query changes, or `make generate` when
other generated inputs also changed. `make db-migrate` applies store migrations
with Goose's `-allow-missing` option; Hub migrations run automatically at startup.

sqlc and Templ Go output retain the Git merge attribute unset. Merge their
source inputs, then regenerate and stage only that Go output with `make generate`;
choosing one branch's output does not resolve the combined source. Ordinary
source files retain Git's text merge behavior.

This source convention does not add a required check, strict branch freshness,
merge worker, or recovery path. It exposes these collisions to existing Git
conflict handling; unrelated semantic conflicts still rely on review and the
scheduled suite.

## Generated artifact inventory

| Artifact | Source | Owner |
| --- | --- | --- |
| `docs/config.md` and `config.reference.yaml` | Authored `docs/config.md.in`, typed config, defaults and validators | `make generate-docs`, tests and docs publish; ignored |
| `static/css/output.css` | `static/css/input.css`, templates and npm lockfile | `make assets` at build time; ignored |
| `static/app/conversation/**` | `web/conversation` source and npm lockfile | `make assets` at build time; ignored |
| `internal/store/sqlc/*.go` | SQL queries, migrations and pinned sqlc config | Committed: plain `go build` needs these types and query methods |
| `internal/web/**/*_templ.go` | Templ sources and pinned Templ version | Committed: plain `go build` needs the generated render functions |

Go does not run generators during compilation. The two generated-Go exceptions
allow a plain checkout to build and test with Go alone. All other generated
outputs are ignored. `make build` prepares assets and docs without regenerating
tracked Go; `make generate` explicitly regenerates Go after source changes.
Vendored JavaScript/fonts, authored OpenAPI, SQL migrations and reviewed test
fixtures are inputs, not outputs of these generators.

`make test` and `make test-fast` generate docs before testing.
`make check-generated` generates config docs and retains `sqlc diff` only for
committed SQL output. The scheduled suite runs this target on its pinned commit, so
generator failures still fail scheduled validation. It does not compare ignored
output with Git. Optional `configdoc -check` compares existing local output with
fresh rendering; plain `go test` does not require generated docs.

## Visual tests

Playwright layout tests live under `tests/visual/` and run against isolated
`detent dev-runtime` instances on port `0`. Install Chromium once, then run:

```sh
npx playwright install chromium
make visual-e2e
```

Every host runs the same browser journeys and outcome assertions. UI changes
attach screenshots (light/dark, desktop/390 as relevant) to the issue or PR as
review evidence for human or AI comparison against the approved design.
Screenshots are never compared by pixels or hashes in any test or gate.

Do not commit `tmp/playwright-evidence`, `tmp/playwright-report`, or
`tmp/playwright-results`.

## Published documentation

The detent.build `cmd/docs-sync` consumer must materialize its verified pinned
upstream commit as a full source tree, then run `make generate-docs` in that
tree before selecting published files. This needs Go 1.26, not Node or the
sqlc/Templ executables. Keep its tag-object and peeled-commit verification.
Copy authored docs from that same tree and include generated `docs/config.md`.
Exclude the input `docs/config.md.in` from the published inventory. Hash generated content for the existing manifest;
there is no Git blob OID for ignored outputs. Preserve the source commit/tag
provenance and existing publication transaction. A Git-only `ls-tree` or
`git show` docs sync cannot publish the generated pages.

Do not advance the site's pinned upstream release to this layout until that
companion source update is available. Site publication remains separate from
Detent's build and scheduled validation.

## Hub analytics rollups

Diagnostics, Reports and `analytics_dashboard` read the persisted
`analytics_hourly_rollups` model through the WAL reader pool. Ready decisions,
skip reasons, merge entries and lease capacity have additive hourly values.
Residence reads subtract accumulated per-issue lane and queue durations from
hourly snapshots. Indexed state-boundary samples supply exact partial-hour
edges, Todo depths and population clipping. Open spans contribute elapsed time
from their recorded start without a timer or event replay. Completion samples
retain the accumulated durations at Done for completion quantiles and throughput.
Claim waits have additive hourly durations; indexed claim and skip samples retain
bounded population cursors. The same model retains current issue, attempt and
usage facts for exact quantiles and distinct populations. It excludes observation-event
payload history. Landing and refusal identities remain bounded drill-downs.

The existing native commit path projects changed work items before committing,
using the board's existing dirty-item list and per-item event sequence positions.
Residence maintenance resumes from the last stored per-issue sequence and
processes only new transitions and claims. There is no periodic analytics worker.
Unchanged lease snapshots do not rewrite
capacity buckets. Lease capacity buckets extend at most 24 hours past the projecting
commit; a lease renewal reprojects them. Each work item projects inside its own savepoint: analytics failure does not
roll back an event, claim or lane transition, or another item's projection. A
failed item keeps its last sequence position and is marked failed; every later
commit retries it, and its project reads as unavailable rather than serving old
totals as complete until the retry succeeds.

`rebuildAnalyticsRollups` rebuilds one organization/project in a caller-owned
transaction from the raw source views, including the hourly counters, residence snapshots, completion and decision
samples, and lease buckets. Schema migrations backfill all existing projects. Changes to metric
definitions must update those source views and rebuild the affected projections
in their migration. Rebuilds preserve tenant scope and replace the project's
rollups and sequence positions atomically.

Compaction does not delete rollups. Scheduler claim samples retain their exact
predecessor before raw observation rows can be compacted. A rebuild after
compaction cannot recreate deleted predecessor evidence: a sequence gap makes
that capacity-wait interval unavailable. It must not infer adjacency from the
next surviving earlier event. Current runtime observations and usage remain
rebuildable from their durable source records.

## Conversation assets

Conversation source and its npm lockfile are tracked; `static/app/conversation/`
is ignored build output. Do not stage that directory in feature commits.
`make app` installs the locked dependencies and builds the entire client.
`make assets` also prepares the dashboard stylesheet.
`make generate` runs it before Go generators, and `make build` embeds that
output. Use Node 24 for the same toolchain as staging and release builds.

For a private operator build, first select the complete source composition in
this isolated checkout, then run `make build`. When supplying custom Go flags
or cross-compiling, run `make assets` followed by the desired `go build` command.
Always regenerate after changing or integrating client source or the lockfile;
a direct Go build cannot determine whether existing ignored output is stale.
A plain checkout compiles without Node or generated assets. Its embedded tree
contains the tracked static inputs; prepare assets before running the UI.
The existing missing-client response applies to an unprepared binary.
Prepared release source archives already contain the embed inputs and
`BUILD_LDFLAGS`, so end users compile those with Go alone.

Staging and scheduled fresh-checkout consumers call the repository's
`prepare-conversation` action, which uses this same `make assets` entry point.
GoReleaser's before hook prepares assets and docs for release and snapshot
builds and includes all output in its prepared source archive. Every consumer
builds from its pinned checkout; assets from a different feature branch are never reused.

`make check-app` retains typechecking, client unit tests, rebuilding and
attribution diagnostics. It does not compare against committed bundles and is
not a shipping gate. The scheduled suite validates integrated source as before.

To reproduce the contention regression and exercise embedded delivery, run:

```sh
python3 scripts/verify-conversation-build.py
```

The diagnostic creates a repository under the provided worker scratch directory,
merges two independent client edits with source-only commits, builds a local
GoReleaser snapshot, and compiles its prepared source with Go alone. Both builds
exercise the existing embedded HTTP handler for every conversation asset from
an arbitrary working directory. It neither publishes a release nor touches
tracker state, shared refs or the running service.
